# Flutter 发布部署说明

本文说明当前 Flutter 客户端的版本更新、编译、部署和更新说明写法。

## 当前发布入口

- 根目录脚本：`./deploy.sh`
- Flutter 版本号来源：`flutter_app/pubspec.yaml` 的 `version`
- App 更新接口元数据来源：`deploy.sh` 读取 `flutter_app/release-notes.txt` 后生成的 `version.json`
- 版本历史来源：`flutter_app/release-history.json`，每个版本独立保存版本号、构建号和更新条目

## 版本更新

发布前先更新 `flutter_app/pubspec.yaml`：

```yaml
version: 1.3.26+33
```

说明：

- `1.3.26` 是展示给用户看的版本号
- `33` 是 Android `versionCode`
- `lib/core/services/app_updater.dart` 会用后端返回的 `version_code` 和本地 `buildNumber` 比较，远端更大才提示更新

## 本地编译

在 `flutter_app` 目录下执行：

```bash
flutter pub get
flutter analyze
flutter test
flutter build apk --release
flutter build web --base-href /
```

产物位置：

- APK：`flutter_app/build/app/outputs/flutter-apk/app-release.apk`
- Web：`flutter_app/build/web/`

## 一键部署

在项目根目录执行：

```bash
./deploy.sh
```

如果只是发布 Flutter 前端，执行：

```bash
./deploy.sh --frontend-only
```

当前脚本会按顺序做这些事：

1. 读取 `flutter_app/pubspec.yaml` 中的 `version` 作为版本号和版本编码
2. 构建后端 Linux 二进制
3. 构建 Flutter Web，并打包为 tar.gz
4. 构建 Flutter Android APK
5. 构建 CLI 三平台产物
6. 生成 APK 更新元数据 `version.json`
7. 上传后端、Web、APK、CLI 到服务器
8. 重启后端并校验线上下载地址

## 服务端更新说明来源

Flutter App 内的更新弹窗读取：

- 接口：`/api/app/version`
- 字段：`version`、`version_code`、`download_url`、`changelog`、`releases`

这些字段当前由 `deploy.sh` 读取 `flutter_app/release-notes.txt` 和 `flutter_app/release-history.json` 后生成：

```bash
APP_CHANGELOG_FILE="flutter_app/release-notes.txt"
APP_RELEASE_HISTORY_FILE="flutter_app/release-history.json"
python3 - "$VERSION_NAME" "$VERSION_CODE" "$PUBLIC_BASE" "$APP_CHANGELOG_FILE" "$APP_RELEASE_HISTORY_FILE" "$VERSION_JSON_LOCAL" <<'PY'
import json, pathlib, sys
version, code, base, notes_file, history_file, output = sys.argv[1:]
notes = pathlib.Path(notes_file).read_text(encoding="utf-8").strip()
history = json.loads(pathlib.Path(history_file).read_text(encoding="utf-8"))
current = {
  "version": version,
  "version_code": int(code),
  "released_at": "",
  "items": [line[2:].strip() if line.startswith("- ") else line for line in notes.splitlines() if line.strip()],
}
releases = [current] + [item for item in history if item["version_code"] != int(code)]
payload = {
  "version": version,
  "version_code": int(code),
  "download_url": f"{base}/api/app/download?v={code}",
  "changelog": notes,
  "releases": releases,
}
pathlib.Path(output).write_text(json.dumps(payload, ensure_ascii=False), encoding="utf-8")
PY
```

客户端更新历史接口为 `/api/app/releases`。发布时只把当前版本内容写入
`release-notes.txt`；历史版本放在 `release-history.json`，不会再将多个版本说明
拼接成当前版本的一条更新内容。

## 更新说明怎么写

建议控制在 2 到 4 条，每条一句话，直接描述用户能感知到的变化。

写法建议：

- 先写用户问题或收益，不写内部重构细节
- 优先写修复项、行为变化、兼容性变化
- 一条只说一件事，避免长句
- 弹窗空间有限，尽量每条 18 到 36 个汉字左右

推荐模板：

```text
- 修复 Android 与 iOS 某某场景下无法正常使用的问题
- 优化 某某交互，在某某情况下表现更稳定
- 新增 某某能力，满足某某使用场景
```

本次这个功能适合写成：

```text
- 修复 Android 与 iOS 长按粘贴长文本时未转为 .txt 附件的问题
- 保留桌面端 Ctrl+V 或 Cmd+V 的长文本转文件行为，并与移动端粘贴菜单保持一致
- 超过 500 字符的剪贴板文本现在会统一作为 text/plain 附件发送，避免输入框被大段文本撑满
```

## 发布前检查

建议至少确认这些内容：

1. 设置页里“粘贴长文本为文件”开关可正常开关
2. Android 真机长按输入框点“粘贴”后，超过 500 字符的文本会变成 `.txt` 附件
3. iOS 真机长按输入框点“粘贴”后，超过 500 字符的文本会变成 `.txt` 附件
4. 桌面端 `Ctrl+V` 或 `Cmd+V` 仍然保持原有行为
5. 发送后的用户消息下方能看到附件卡片
6. 线上 `/api/app/version` 返回的 `version_code` 与 `pubspec.yaml` 一致
7. 线上 APK 下载地址可访问

## 回滚关注点

这次改动只涉及前端输入层和更新说明：

- 粘贴入口从键盘快捷键扩展到了移动端上下文菜单
- 没改后端接口结构
- 如果需要回滚，优先回滚 `chat_page.dart` 和 `deploy.sh` 的本次改动即可
