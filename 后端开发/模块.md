# 后端模块设计

## 目标

构建一个稳定、低损耗、便于远程控制的后端控制中心，负责接收移动端请求、维护设备在线状态、将任务转发给改造后的 `OpenCode serve`，并保证同一任务可以持续复用同一个会话。

推荐架构：

```text
移动端 / Web
-> 后端控制中心（Go）
-> WebSocket
-> 改造后的 OpenCode serve
-> 本地代码仓库 / shell / MCP
```

## 模块划分

### 1. 接入层模块

职责：

- 对外提供 `HTTPS API`
- 提供移动端鉴权
- 接收创建任务、查询任务、继续会话、停止任务等请求
- 提供任务事件流查询入口

建议接口：

- `POST /api/login`
- `POST /api/tasks`
- `GET /api/tasks/:taskId`
- `GET /api/tasks/:taskId/events`
- `POST /api/tasks/:taskId/cancel`
- `POST /api/tasks/:taskId/approve`
- `GET /api/sessions/:sessionId`

实现步骤：

1. 先完成基础 HTTP 服务启动与路由注册
2. 加入 JWT 或长期 token 鉴权
3. 定义统一返回结构和错误码
4. 加入请求日志、中间件、超时控制

关键细节：

- 所有外部请求必须带用户身份
- 任务创建接口不能直接执行 shell，只能创建任务并下发给设备层
- 事件查询建议优先支持 `SSE`，移动端后续可再补 `WebSocket`

### 2. 设备连接模块

职责：

- 维护开发机或执行机与服务器之间的长连接
- 管理设备上线、下线、心跳、重连
- 将任务定向发送到正确设备

建议协议：

- 通信方式：`WebSocket`
- 消息格式：`JSON`

建议消息类型：

- `device.hello`
- `device.heartbeat`
- `device.status`
- `task.run`
- `task.cancel`
- `task.delta`
- `task.completed`
- `task.failed`
- `task.approval_required`
- `task.approval_response`

实现步骤：

1. 建立设备 WebSocket 接入端点
2. 完成设备鉴权与注册
3. 维护在线设备表
4. 完成心跳检测和断线清理
5. 完成任务定向下发

关键细节：

- 一个设备需要有稳定 `device_id`
- 断线后要立刻标记设备不可调度
- 同一仓库同一时刻默认只允许一个执行任务，避免上下文互相污染

### 3. 任务调度模块

职责：

- 接收用户任务
- 根据仓库、设备、会话状态分配任务
- 管理任务生命周期

任务状态建议：

- `pending`
- `dispatched`
- `running`
- `waiting_approval`
- `completed`
- `failed`
- `cancelled`

实现步骤：

1. 定义任务表结构和状态机
2. 创建任务时绑定用户、项目、设备、目标分支
3. 按设备可用性和项目锁进行调度
4. 接收设备回传状态并更新数据库

关键细节：

- 新任务与继续会话要区分
- 如果是继续会话，必须带已有 `session_id`
- 需要对同项目并发执行做锁控制

### 4. 会话管理模块

职责：

- 保证同一对话持续复用同一个 `OpenCode session`
- 维护外部任务与内部 `session_id` 的映射关系

核心字段：

- `session_id`
- `device_id`
- `project_id`
- `user_id`
- `last_task_id`
- `status`

实现步骤：

1. 创建 session 映射表
2. 新会话任务首次生成 `session_id`
3. 后续任务复用原会话
4. 断线恢复后允许按 `session_id` 继续

关键细节：

- 会话不应只存在内存里，必须持久化
- 任务与会话是一对多关系
- 会话恢复失败要给出明确错误，不要静默重建新会话

### 5. OpenCode 中转模块

职责：

- 将设备收到的任务转发给改造后的 `OpenCode serve`
- 订阅其流式输出
- 标准化转发给服务器

实现步骤：

1. 明确 `OpenCode serve` 的内部调用接口
2. 统一任务输入结构
3. 统一流式输出结构
4. 增加错误分类

关键细节：

- 这一层只做协议转换和状态同步，不要掺入业务逻辑
- 需要支持流式 token 输出、工具事件、最终结果事件
- 要保留原始错误信息，方便排查模型调用或工具失败

### 6. 审批与安全模块

职责：

- 控制高风险操作
- 提供远程审批链路
- 防止设备执行超出预期的危险命令

高风险操作示例：

- 删除大量文件
- `git push`
- 部署命令
- 数据库结构变更
- 写入敏感路径

实现步骤：

1. 定义风险动作分类
2. 设备端上报审批请求
3. 服务器挂起任务状态
4. 用户审批后再恢复执行

关键细节：

- 审批结果必须落库
- 审批超时要可配置
- 被拒绝后任务状态要明确标记为失败或取消

### 7. 存储模块

职责：

- 持久化用户、设备、任务、会话、事件日志

推荐：

- 主数据库：`PostgreSQL`

建议表：

- `users`
- `devices`
- `projects`
- `sessions`
- `tasks`
- `task_events`
- `task_approvals`

实现步骤：

1. 设计基础表结构
2. 为任务状态和会话查询建立索引
3. 将事件流按 task_id 持久化
4. 增加审计字段

关键细节：

- `task_events` 会增长很快，要提前设计分页和清理策略
- 所有关键表都需要 `created_at` 和 `updated_at`
- 任务和事件不能只存最终结果，中间过程也要保存

### 8. 观测与运维模块

职责：

- 监控在线设备
- 观察任务执行耗时
- 记录异常

实现步骤：

1. 引入结构化日志
2. 增加基础健康检查接口
3. 统计设备在线数、任务执行数、失败率
4. 增加关键错误告警

关键细节：

- 设备掉线要能快速看到
- 长时间无心跳设备要自动剔除
- 任务失败原因要能区分模型问题、网络问题、工具失败、审批拒绝

## 推荐实施顺序

### 第一阶段：跑通最小链路

1. 创建 Go 后端项目骨架
2. 完成 HTTP 服务和 WebSocket 设备连接
3. 完成设备注册、心跳、任务下发
4. 完成最小任务表和事件表
5. 跑通一条任务从移动端到设备再到结果回传的链路

交付标准：

- 可以创建任务
- 可以给在线设备下发任务
- 可以拿到流式结果
- 可以保存 `session_id`

### 第二阶段：保证同一会话与稳定性

1. 完成 session 持久化和恢复
2. 完成任务状态机
3. 完成同项目互斥锁
4. 完成断线重连与重试策略

交付标准：

- 同一对话可持续复用
- 设备断线后系统状态正确
- 不会出现同仓库并发污染

### 第三阶段：补安全与产品化能力

1. 增加审批流
2. 增加审计日志
3. 增加任务筛选与历史查询
4. 增加限流和超时控制

交付标准：

- 高风险动作可审批
- 任务全链路可追踪
- 可以支持真实移动端使用

## 不建议的实现方式

- 不建议把服务器中转逻辑放进 OpenCode 插件
- 不建议先做多设备复杂调度
- 不建议第一版就引入过多中间件
- 不建议直接把 `OpenCode serve` 暴露到公网

## 当前推荐技术选型

- 后端语言：`Go`
- HTTP 路由：`chi`
- WebSocket：`github.com/coder/websocket`
- 数据库：`PostgreSQL`
- 数据访问：`pgx`
- 日志：`zerolog` 或 `zap`
- 配置：`env + yaml`
