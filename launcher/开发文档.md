# Launcher 开发文档

## 目标

`launcher` 是独立于 `my-opencode` 的设备侧守护程序，负责管理当前设备上的多个 `my-opencode serve` 实例。

第一阶段目标：

1. 维护当前设备上的多 agent 实例清单
2. 获取当前设备可用目录并用于创建新 agent
3. 启动并守护多个 `my-opencode serve` 实例
4. 支持远程升级到指定版本
5. 升级失败自动回滚
6. 支持三端二进制发布
7. 与当前后端控制链路对接

不承担的职责：

1. 不承担 AI 配置、任务执行、Relay 业务逻辑
2. 不直接修改 `my-opencode` 内部业务状态
3. 不做热更新
4. 第一阶段不做差分升级

## 设计原则

1. `launcher` 做设备级治理，不做单个 agent 的业务执行
2. `launcher` 负责多 agent 生命周期、目录发现、升级与回滚
3. `my-opencode serve` 负责单个 agent 的业务服务
4. 运行中的 `serve` 不直接覆盖自己
5. 升级必须先下载到新版本目录，再切换当前版本指针
6. 启动成功必须经过健康检查确认
7. 升级必须有锁，避免并发升级
8. 回滚必须自动化，不允许失败后停死
9. 默认纯 Go 实现，避免 CGO

## 推荐技术栈

语言：Go

原因：

1. 适合做长期驻留 supervisor
2. 适合子进程拉起、等待、停止、重启
3. 适合本地文件、锁、状态机、升级编排
4. 可直接在 mac 上交叉编译三端二进制
5. 不依赖目标机器额外运行时

建议编译参数：

```bash
CGO_ENABLED=0
```

## 架构边界

### launcher 的职责

1. 维护设备级状态
2. 维护 agent 实例清单
3. 扫描和返回当前设备可用目录
4. 按目录创建新的 agent 实例
5. 启动、停止、重启、删除指定 agent
6. 统一管理 `my-opencode` 运行版本
7. 负责升级、回滚、重启后的恢复
8. 向后端汇报设备级状态和实例状态

### my-opencode serve 的职责

1. 承载单个 agent 的业务能力
2. 只服务于单个项目目录
3. 只管理自己这个 agent 的任务、配置、会话
4. 不负责扫描设备目录
5. 不负责启动其他 agent 实例
6. 不负责设备级升级编排

### 最终模型

设备上实际运行模型应为：

```text
launcher
  ├─ opencode serve (agent A, project dir A)
  ├─ opencode serve (agent B, project dir B)
  └─ opencode serve (agent C, project dir C)
```

也就是说，`launcher` 是设备根控制器，`my-opencode serve` 是被管理的 agent 实例。

## 本地运行目录规划

建议 `launcher` 在设备上维护专属运行目录：

```text
~/.my-opencode-launcher/
  state.json
  launcher.log
  current
  agents.json
  agents/
    agent-a/
      config.json
      stdout.log
      stderr.log
    agent-b/
      config.json
      stdout.log
      stderr.log
  versions/
    1.4.8/
      opencode
      manifest.json
    1.4.9/
      opencode
      manifest.json
  downloads/
  work/
  logs/
    serve.stdout.log
    serve.stderr.log
```

说明：

1. `current`：当前生效版本目录指针
2. `agents.json`：设备上的 agent 实例清单
3. `agents/<agent-id>/config.json`：单个 agent 的启动配置
4. `versions/`：每个版本一个独立目录
5. `downloads/`：临时下载包
6. `work/`：升级中的临时解压目录
7. `state.json`：设备级状态、版本、错误信息
8. `logs/`：通用日志目录
9. `agents/<agent-id>/stdout.log` / `stderr.log` 会继续保留，同时 launcher 可实时镜像到当前控制台

## Agent 实例模型

建议每个 agent 记录以下信息：

```json
{
  "agent_id": "agent_a1b2c3",
  "name": "chat-codex",
  "project_dir": "/Users/yuminghao/Downloads/chat-codex",
  "status": "running",
  "pid": 12345,
  "port": 4096,
  "version": "1.4.8",
  "created_at": "2026-04-14T22:00:00Z",
  "updated_at": "2026-04-14T22:10:00Z"
}
```

建议 `agents.json` 保存所有实例的摘要信息，单个实例详细配置放在各自目录下。

## 核心流程

### 1. 启动流程

`launcher` 启动后执行：

1. 读取本地配置
2. 初始化运行目录
3. 读取 `state.json`
4. 读取 `agents.json`
5. 确认 `current` 指向的版本是否存在
6. 遍历需要自动恢复的 agent 实例
7. 为每个实例生成子进程启动命令
8. 启动对应的 `my-opencode serve`
9. 对每个实例执行健康检查
10. 成功后把设备状态改为 `running`
11. 失败则进入恢复或退出流程

### 2. 守护流程

运行中持续做三件事：

1. 监控所有 agent 子进程退出
2. 上报设备状态与 agent 列表
3. 处理控制命令

子进程异常退出时：

1. 若当前不是升级态，则按实例重启策略自动拉起该 agent
2. 若当前是升级态，则按升级失败流程处理

### 3. 目录发现与创建新 Agent

推荐时序：

1. 接收“获取设备目录”请求
2. 返回允许范围内的目录列表
3. 接收“按目录创建 agent”请求
4. 校验目录存在且为文件夹
5. 校验目录未被重复占用，或按策略允许多开
6. 为新实例生成 `agent_id`
7. 写入 `agents.json` 和 `agents/<agent-id>/config.json`
8. 使用当前 `current` 版本启动新的 `my-opencode serve`
9. 执行该实例的健康检查
10. 成功则返回新 agent 信息
11. 失败则清理脏状态并返回错误

### 4. 升级流程

推荐时序：

1. 收到目标版本升级命令
2. 获取升级锁
3. 状态切换到 `upgrading`
4. 查询后端版本元数据
5. 下载对应平台安装包
6. 解压到 `work/`
7. 校验二进制存在且版本匹配
8. 写入 `versions/<target>/`
9. 停止当前所有 agent 实例
10. 切换 `current` 到新版本
11. 按实例清单重新启动所有 agent
12. 对每个实例做健康检查
13. 成功则状态切到 `running`
14. 任一关键实例失败则进入回滚

### 5. 回滚流程

1. 停止启动失败的新版本实例
2. 将 `current` 切回上一版本
3. 按实例清单重启上一版本 agent
4. 健康检查通过后标记 `running`
5. 上报 `rollback_succeeded`
6. 若旧版本也拉不起来，状态进入 `failed`

## 状态机设计

建议状态值：

1. `idle`
2. `starting`
3. `running`
4. `stopping`
5. `upgrading`
6. `rollbacking`
7. `failed`

建议状态文件：

```json
{
  "status": "running",
  "current_version": "1.4.8",
  "target_version": "1.4.9",
  "previous_version": "1.4.8",
  "started_at": "2026-04-14T22:00:00Z",
  "updated_at": "2026-04-14T22:10:00Z",
  "last_error": "",
  "agent_count": 3,
  "upgrade_locked": false
}
```

字段说明：

1. `status`：当前生命周期状态
2. `current_version`：当前生效版本
3. `target_version`：正在升级的目标版本
4. `previous_version`：回滚用上一版本
5. `last_error`：最近错误信息
6. `agent_count`：当前设备上管理的 agent 数量
7. `upgrade_locked`：是否存在升级锁

## 本地配置建议

建议 `launcher` 维护独立配置文件，例如：

```json
{
  "runtime_dir": "~/.my-opencode-launcher",
  "listen_addr": "127.0.0.1:4071",
  "agent": {
    "binary_name": "opencode",
    "base_args": ["serve", "--hostname", "0.0.0.0"],
    "env": {
      "OPENCODE_SERVER_PASSWORD": "***"
    },
    "print_logs": true
  },
  "directory_discovery": {
    "allowed_roots": [
      "~/Downloads",
      "~/workspace"
    ],
    "include_cwd": true,
    "include_recent": true,
    "max_depth": 2
  },
  "health": {
    "timeout_seconds": 20,
    "interval_millis": 500
  },
  "update": {
    "base_url": "https://www.xyapi.top/codex",
    "channel": "latest",
    "allow_prerelease": false
  },
  "restart": {
    "max_attempts": 5,
    "backoff_millis": 2000
  }
}
```

环境变量补充：

1. `LAUNCHER_PRINT_AGENT_LOGS=1`：默认开启，将 agent 的 stdout/stderr 实时输出到 launcher 当前命令行
2. `LAUNCHER_PRINT_AGENT_LOGS=0`：关闭实时镜像，仅保留本地 `stdout.log` / `stderr.log`

## 平台处理建议

### macOS

1. 二进制文件可直接替换版本目录内容
2. 推荐通过 `launcher` 切换 `current` 指针
3. 可结合 `launchd` 托管 `launcher`

### Linux

1. 行为与 macOS 接近
2. 推荐生产环境用 `systemd` 托管 `launcher`
3. `launcher` 再托管 `serve`

### Windows

1. 文件替换需要更谨慎处理占用问题
2. 不能直接覆盖运行中的可执行文件
3. 应先停止旧进程，再替换版本目录，再拉起新进程
4. 建议 `launcher` 自身也尽量避免自覆盖，后续单独处理 launcher 自身升级

## Launcher 自身升级建议

第一阶段不建议把 `launcher` 自身升级也做进去。

原因：

1. `launcher` 已经是守护层，再自升级会显著增加复杂度
2. 先把 `my-opencode serve` 的升级和回滚闭环跑通更重要

建议阶段划分：

### 阶段 1

1. `launcher` 固定版本
2. 只管理多个 `my-opencode serve` 实例

### 阶段 2

1. 增加 `launcher` 自身升级器
2. 由更外层系统服务托管 `launcher`

## 健康检查建议

优先级建议：

1. 本地 HTTP health 接口
2. 指定端口连通
3. 设备重新向后端成功注册

第一阶段推荐组合：

1. `serve` 监听端口可访问
2. 本地 `/health` 返回正常

若后面需要更严谨，可追加：

1. 与后端 websocket 重连成功才算升级完成

## 日志建议

建议将日志拆两类：

1. `launcher.log`
2. 各 agent 的 `stdout.log` / `stderr.log`

每次升级、回滚、重启要记录：

1. 目标版本
2. 下载地址
3. 校验结果
4. 启动结果
5. 回滚结果
6. 最终状态

## 最小可用实现顺序

建议按下面顺序开发：

1. 完成 `launcher` 基础目录和配置读取
2. 实现子进程启动、停止、重启
3. 实现状态文件写入
4. 实现本地 health 检查
5. 实现版本目录切换
6. 实现下载和解压
7. 实现升级锁
8. 实现失败自动回滚
9. 实现本地控制接口
10. 对接后端远程升级协议

## 建议的 Go 包拆分

### `internal/process`

职责：

1. 启动子进程
2. 发送退出信号
3. 等待退出
4. 重定向 stdout/stderr

### `internal/release`

职责：

1. 管理 `versions/`
2. 创建 `current` 指针
3. 获取当前版本
4. 切换到目标版本

### `internal/download`

职责：

1. 下载版本包
2. 校验大小与 hash
3. 解压 zip / tar.gz

### `internal/health`

职责：

1. 本地 HTTP 健康检查
2. 超时重试
3. 返回是否启动成功

### `internal/state`

职责：

1. 读写 `state.json`
2. 管理状态切换
3. 记录最近错误

### `internal/control`

职责：

1. 本地控制 HTTP 接口
2. 参数校验
3. 将命令交给 `app` 执行

## 三端编译方案

建议脚本：

```bash
CGO_ENABLED=0 GOOS=darwin GOARCH=arm64 go build -ldflags="-s -w" -o dist/launcher-darwin-arm64 ./cmd/launcher
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -ldflags="-s -w" -o dist/launcher-linux-x64 ./cmd/launcher
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -ldflags="-s -w" -o dist/launcher-windows-x64.exe ./cmd/launcher
```

打包建议：

1. macOS -> zip
2. Linux -> tar.gz
3. Windows -> zip

可与现有 `my-opencode/packages/opencode/script/build-three.ts` 类似，再做一个 launcher 专用打包脚本。

## 风险点

1. Windows 文件占用与替换最容易出问题
2. 如果健康检查不准确，可能误判启动成功
3. 升级锁设计不好会出现并发升级
4. 多 agent 端口分配策略不当会导致实例冲突
5. 同一路径的重复启动策略如果不明确，容易出现脏实例
6. 版本清理策略不当会导致磁盘积累过多旧版本
7. `launcher` 自身升级不应在第一阶段实现

## 第一阶段验收标准

满足以下条件即可认为第一阶段完成：

1. `launcher` 能启动并守护 `my-opencode serve`
2. `launcher` 能返回当前设备可用目录
3. 可按目录创建新的 agent 实例
4. `serve` 实例异常退出后能自动拉起
5. 能升级到指定版本
6. 升级失败能自动回滚
7. 新版本启动成功后状态正确
8. 能编译出 macOS、Linux、Windows 三端二进制
9. 后端可查看升级结果、设备状态与 agent 列表

## 建议的后续开发顺序

1. 先搭 `launcher` 最小骨架
2. 先跑通目录发现与创建单个 agent
3. 再跑通多 agent 启动与守护
4. 再做版本目录切换
5. 再做升级与回滚
6. 最后接入后端控制面

## 备注

当前仓库已经具备：

1. `my-opencode` 三端构建能力
2. 后端 CLI 版本分发能力
3. 设备 websocket 通道

所以 `launcher` 不需要重新发明分发系统，只需要把：

1. 版本下载
2. 守护
3. 重启
4. 回滚
5. 状态上报

这几件事补全即可。
