# 反代 × Chat Codex 会员分级联动方案 v2（零人工 · 控制台只做配置与监控）

> v1 的做法需要人工建钥匙、人工写设备配置；v2 的目标是**日常流程全自动**，
> 人工只出现在两处：**控制台改策略**（配置）与**应急操作**（轮换/加额/禁用）。

## 〇、零人工闭环一览（核心表）

| 触发（无需人工） | 系统自动动作 | 组件 |
|---|---|---|
| **用户在 App 里核销兑换码**（唯一入口，无支付、无人工） | 自动改会员等级/延长到期 → 自动建或更新网关钥匙 → 自动下发到该用户**全部在线设备** | `RedeemService` → `Provisioner` → `Deliverer` |
| 用户在**新设备**登录 / 设备心跳上报（`device.heartbeat`） | **自愈**：该设备缺专属 provider 就自动补推（含密钥与模型包） | `Deliverer`（心跳钩子 + 兜底巡检） |
| 控制台**改等级策略**（模型包 / 额度 / provider 名） | 自动把变更推给**该等级全体用户**的钥匙与设备（批量、分片、可回滚） | `Provisioner.EnqueueTier(tier)` |
| 网关**模型目录变化**（新增/下线模型、调价） | 自动同步目录与价格到平台；按规则自动归档到等级（未匹配的进"待认领"队列，控制台点一下即可） | `CatalogSync` |
| 用量增长 / 跨日 | 定时拉 `/admin/keys` + `/admin/usage` 落库；跨日自动重置（网关 UTC 日翻滚） | `UsageSync` |
| 额度耗尽（网关已自拒） | 平台标记 `exhausted` → App 明确提示 → 用户续费后**自动**加额并恢复 | `QuotaGuard` |
| 订阅到期 / 退款 / 降级 | 自动收紧模型包、下调额度、必要时禁用钥匙、撤除设备专属 provider | `Provisioner` + `Deliverer` |
| 网关不可用 / 超时 / 5xx | **幂等重试 + 补偿队列**；网关恢复后自动补齐收敛（设备配置在新配置确认前保持旧值，不破坏可用性） | `GatewayClient` |
| 异常（同一钥匙多设备高频、403 激增、密钥疑似泄露） | 自动告警 → 可选自动轮换钥匙 | `Audit & Alert` |

**一句话**：平台把"等级"当成期望状态（desired state），后台有一个**持续收敛的 reconciler**——只要有人/系统改了等级，钥匙、设备配置、额度、用量展示都会自己跟上。

## 一、分工

- **网关（cmdproxy）= 账本 + 门禁**：钥匙 = 模型包 + 额度包；请求时强校验、超限拒绝、逐条记账。（现有能力，只补一处：`/v1/models` 按 key 过滤）
- **平台 = 期望状态的唯一持有者 + 自动驾驶**：等级 → 钥匙 → 设备配置 → 用量展示，全链路自动。
- **App = 零改动**（模型列表自动出现；可选加一个"我的额度"页）。
- **控制台 = 配置 + 监控 + 应急**（不做日常操作）。

## 二、能力盘点（代码实测）

### 网关 `cmdproxy/gateway`（3711 行 Go）

## 三、零人工的四个自动组件（平台新增）

```
┌──────────────────────────── 平台 ────────────────────────────┐
│  RedeemService   兑换码核销（App 内）→ 等级/到期/额度（幂等）    │
│        ↓ 期望状态（tier + 到期时间）                          │
│  Provisioner   等级 → 钥匙（建/改/禁用）+ 变更广播             │
│        ↓                                                     │
│  Deliverer     钥匙 → 用户全部设备 AI 配置（心跳自愈 + 巡检）   │
│        ↓                                                     │
│  UsageSync     网关用量 → 日汇总落库 → App 展示                │
│  QuotaGuard    额度耗尽/到期 → 自动处置（禁用/降级/恢复）        │
│  CatalogSync   网关模型目录与价格 → 平台目录 → 等级归档         │
│  GatewayClient 幂等重试 + 补偿队列 + 熔断（网关抖动不丢状态）    │
└──────────────────────────────────────────────────────────────┘
```

### 状态机（每个用户一行，全部自动流转）

```
desired: tier(free|plus|pro) + expires_at + policy_version
   │
   ├─ provisioning   → 正在建/改钥匙（可重试）
   ├─ delivering     → 正在下发设备配置（按设备逐台确认）
   ├─ active         → 钥匙有效 + 设备配置就绪
   ├─ exhausted      → 额度用尽（网关自拒）；续费后自动回 active
   ├─ suspended      → 到期/违规，钥匙 disabled
   └─ revoked        → 钥匙删除（退款/注销）
```

每次自动动作写 `gateway_key_ops` 审计表：`{operator_id, action, desired, attempt, request_id, result, error, at}`，
同一 `operator_id + action + policy_version` **幂等**（重复触发不会重复建钥匙）。

### 幂等与补偿（网关抖动也不丢状态）

- 所有网关调用带 **幂等键**（`gateway_key_ops.request_id`），失败进重试队列：指数退避（5s→1m→10m→1h，上限 24h）。
- 网关 5xx/超时：保持设备配置不变（旧的 provider 仍可用），恢复后自动收敛。
- 钥匙创建**成功但平台未落库**（极端情况）：用 `GET /admin/keys` 按 `name = op_<uid>` 反查认领，避免产生孤儿钥匙。
- 每次收敛幂等：`ensure(operator)` 可任意重复执行。

## 四、等级策略（控制台配置，保存即全量自动生效）

| 等级 | 模型包 | 日额度 | 周期额度 | 备注 |
|---|---|---|---|---|
| free | 维持现状（共享 key + 公共模型） | — | — | 不改现有链路 |
| plus | 例：`deepseek-v4.1-flash`、`glm-5.3-flash` + 1~2 个 plus 专属 | `daily_cost_micro` / `daily_tokens` | `max_cost_micro` | 一把钥匙，多设备共用 |
| pro | plus 全部 + 高级模型（例：`claude-opus-*`、`gpt-5.6-*`） | 更高 | 更高 | 可加 `daily_requests` 防滥用 |

- 模型不是手输字符串：**从网关目录里勾选**（`CatalogSync` 自动拉取 `/admin/models` 与 `/v1/models`，带价格与上游来源）。
- 额度单位用网关的**微单位**（`costMicro`，1e-6 货币），额度=能烧多少钱，天然适配不同模型单价。
- 策略带 `policy_version`：保存后自动对所有该等级用户重算（批量任务 + 分片 + 进度可见）。

## 五、控制台只保留四类页面（配置 + 监控 + 应急）

| 页面 | 作用 | 是否日常必需 |
|---|---|---|
| **① 等级与模型策略** | 勾选每个等级的模型包、设日/周期额度、provider 显示名、是否启用专属 provider；保存即自动全量生效 | 配置（偶尔用） |
| **② 用户与钥匙** | 列表看：等级、钥匙尾号、已用/剩余、最近调用、状态机；支持**应急**：轮换钥匙 / 临时加额 / 立即禁用 / 强制重推设备配置 | 监控（看）+ 应急（极少） |
| **③ 模型目录与价格** | 网关目录自动同步（含上游来源、单价）；可改价；未归档模型进"待认领"列表（一键归档到等级） | 配置（偶尔用） |
| **④ 兑换码** | 批量生成（等级/时长/额度/数量/有效期）→ CSV 导出；批次查看已用未用、按批作废、按码查绑定账号 | 配置（偶尔用，见 §六） |

控制台**不需要**：手工建钥匙、手工写设备配置、手工同步用量、手工处理到期/降级、逐用户开通（全部自动；用户自己兑换即可）。

## 六、会员来源：兑换码（不接支付）

**唯一入口**：用户在 App 里输入兑换码 → 平台核销 → 自动开通并全链路收敛。控制台只负责**批量生成/导出/作废**（配置动作，不是逐人操作）。

### 6.1 码的两种类型（可组合叠加）

| 类型 | 含义 | 核销后效果 |
|---|---|---|
| **会员卡**（tier 卡） | 兑换某个等级的一段时间 | `desired_tier = plus/pro`，`expires_at = max(now, 原 expires_at) + days`（叠加续期） |
| **额度卡**（quota 卡） | 只加额度不改等级 | `max_cost_micro += quota_micro`（或单独一个 bonus 账户） |

同一张码可以两者兼有（`tier=plus, days=30, quota_micro=X`）。

### 6.2 兑换码数据模型

```sql
CREATE TABLE redemption_codes (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  code          VARCHAR(32) NOT NULL,          -- 明文码（建议大写+去易混字符），唯一索引
  code_hash     CHAR(64)    NULL,              -- 需要更严时可只存 hash，控制台仅显示前缀
  batch_id      VARCHAR(64) NOT NULL,          -- 批量生成批次，便于导出/作废
  tier          VARCHAR(16) NULL,              -- 会员卡：plus/pro；NULL=纯额度卡
  days          INT         NULL,              -- 会员卡时长
  quota_micro   BIGINT      NULL,              -- 额度卡面额（微单位）
  max_uses      INT NOT NULL DEFAULT 1,        -- 通常 1；可做多次卡
  used_count    INT NOT NULL DEFAULT 0,
  bound_operator_id BIGINT  NULL,              -- 首次核销即绑定（防转卖/防串用）
  expires_at    DATETIME    NULL,              -- 码本身的有效期
  disabled      TINYINT NOT NULL DEFAULT 0,
  created_by    BIGINT      NOT NULL,          -- 哪个管理员生成的
  created_at / updated_at
);

CREATE TABLE redemption_records (              -- 不可变流水，幂等 + 可审计
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  operator_id BIGINT NOT NULL, code_id BIGINT NOT NULL,
  tier VARCHAR(16) NULL, days INT NULL, quota_micro BIGINT NULL,
  request_id VARCHAR(64) NOT NULL,             -- 幂等键（App 重试不重复核销）
  ip VARCHAR(64), device_id VARCHAR(64),
  created_at DATETIME NOT NULL,
  UNIQUE KEY uk_req (request_id),
  UNIQUE KEY uk_code_once (code_id, operator_id, tier)   -- 单码单用户只生效一次
);
```

### 6.3 核销流程（全自动）

```
App: POST /api/membership/redeem {code, request_id}     ← 幂等键由客户端带
平台:
  1) 校验：码存在、未禁用、未过期、used_count < max_uses、未被别人绑定
  2) 事务内：写 redemption_records（唯一键兜住并发）→ 更新码计数/绑定 → 更新 operators.membership_tier 与 expires_at
  3) 入队收敛（不需要任何人工）：Provisioner → Deliverer
  4) 返回：{ tier, expires_at, models:[...], quota:{used, limit} }  ← App 立刻能展示新等级与专属模型
异常与风控:
  · 同一账号重复提交同一 request_id → 返回首次结果（幂等）
  · 同码并发核销 → 唯一索引拦下，返回"已被使用"
  · 限速：单账号每小时 N 次失败即冷却；失败原因不区分"码不存在/已被用"（防爆破）
```

### 6.4 到期与叠加（无人工）

- 会员卡叠加：续期时 `expires_at = max(now, expires_at) + days`（不清零剩余时间）。
- 到期：定时任务（照抄现有 ticker 模式）扫 `expires_at < now` → 自动降级、收紧钥匙模型包、撤除设备专属 provider、`state=suspended`。
- 额度卡：累加到 `max_cost_micro`；网关那边同步 `PUT /admin/keys/{id}`。
- 退款/回收：控制台可"撤销一次核销"（写反向流水 + 重算期望状态，仍走自动收敛）。

### 6.5 控制台里的兑换码页（配置动作）

- 批量生成：选等级/时长/额度/数量/有效期 → 生成一批 → CSV 导出（或直接复制）；
- 批次管理：查看已用/未用、按批次作废、按码查询绑定账号与核销时间；
- 不需要任何"逐用户开通"的操作。

## 七、平台数据模型（新增；兑换码两张表见 §6.2）

```sql
-- 期望状态 + 钥匙（一用户一行；如需按设备再加 device_id 列）
CREATE TABLE operator_gateway_keys (
  operator_id    BIGINT PRIMARY KEY,
  desired_tier   VARCHAR(16) NOT NULL,
  policy_version INT         NOT NULL,
  state          VARCHAR(16) NOT NULL,      -- provisioning|delivering|active|exhausted|suspended|revoked
  key_id         VARCHAR(64) NULL,
  key_cipher     VARBINARY(256) NULL,       -- 明文钥匙加密存储
  key_last4      CHAR(4) NULL,
  models_json    JSON NULL,                 -- 下发快照
  limits_json    JSON NULL,
  expires_at     DATETIME NULL,
  last_error     TEXT NULL,
  updated_at     DATETIME NOT NULL
);

-- 自动动作审计（幂等 + 可回放 + 控制台可见）
CREATE TABLE gateway_key_ops (
  id             BIGINT AUTO_INCREMENT PRIMARY KEY,
  operator_id    BIGINT NOT NULL,
  action         VARCHAR(32) NOT NULL,      -- ensure_key|update_key|disable_key|revoke_key|push_device|sync_usage
  desired        JSON NULL,
  request_id     VARCHAR(64) NOT NULL,      -- 幂等键（唯一索引）
  attempt        INT NOT NULL DEFAULT 0,
  result         VARCHAR(16) NULL,          -- ok|retry|failed
  error          TEXT NULL,
  created_at / updated_at,
  UNIQUE KEY uk_req (request_id)
);

-- 用量日汇总
CREATE TABLE operator_gateway_usage_daily (
  operator_id BIGINT, day DATE,
  requests BIGINT, prompt_tokens BIGINT, completion_tokens BIGINT, cost_micro BIGINT,
  synced_at DATETIME, PRIMARY KEY (operator_id, day)
);

-- 等级策略（控制台可改）
CREATE TABLE membership_model_policies (
  tier VARCHAR(16) PRIMARY KEY,
  provider_id VARCHAR(64) NOT NULL,         -- 下发到设备的 provider id，如 cc-plus / cc-pro
  display_name VARCHAR(64) NOT NULL,
  models_json JSON NOT NULL,
  limits_json JSON NOT NULL,
  policy_version INT NOT NULL,
  enabled TINYINT NOT NULL DEFAULT 1
);

-- 设备侧下发记录（自愈对账用）
CREATE TABLE operator_device_provider_state (
  operator_id BIGINT, machine_id VARCHAR(64),
  provider_id VARCHAR(64), policy_version INT,
  pushed_at DATETIME, confirmed_at DATETIME NULL, error TEXT NULL,
  PRIMARY KEY (operator_id, machine_id, provider_id)
);
```

## 八、完整自动流程（时序）

```
① 兑换码核销（App 内，用户操作）
   App ──POST /api/membership/redeem {code, request_id}──→ 平台
   平台：幂等校验+事务核销 → desired_tier/expires_at/额度更新 → policy_version++ → 入队
② Provisioner（异步 worker）
   policy = 读策略(tier)
   无钥匙 → GatewayClient.create_key(幂等键)   ← 失败自动重试
   有钥匙 → 与快照比对 → update_key(models, limits)
   落库 + 审计
③ Deliverer（异步 worker + 心跳自愈）
   对该 operator 的全部设备：POST /api/devices/{mid}/ai-config/save
     provider_id/base_url/api_key(=用户钥匙)/models(=策略模型包)
   逐台确认（ai_config.result）→ 写 operator_device_provider_state
   设备心跳时若发现未就绪 → 自动补推（自愈）
④ 用户使用
   设备带钥匙调网关 → 模型校验 + 额度校验 + 记账
⑤ UsageSync（定时，照抄现有 ticker 模式）
   GET /admin/keys（累计）+ /admin/usage（增量）→ 日汇总落库 → App 展示
⑥ QuotaGuard
   额度耗尽 → state=exhausted + App 提示；续费 → 自动加额 → active
   到期 → 收紧模型包/禁用钥匙/撤除设备 provider
```

## 九、改动清单

### 网关（很小）

1. **`/v1/models` 按当前 key 过滤**（必须）：`filterModelList(raw, s.settings.allows)` 之后再按请求 key 的 `Models` 过滤一次；`Models` 为空表示不限制。
2. 可选：`/v1/models` 每项带 `owned_by: cc-plus|cc-pro`（App 分组更清晰）。
3. 可选：额度 80% 回调 webhook（没有就靠平台轮询，v2 默认轮询）。

### 平台

1. `internal/gateway/{client.go,provisioner.go,deliverer.go,usage_sync.go,catalog_sync.go,quota_guard.go}`（新包）。
2. `model/membership_models.go`（新）：`ModelPolicyForTier`、`policy_version` 计算。
3. `POST /api/webhooks/membership`（新，幂等），`GET /api/membership/usage`、`GET /api/membership/models`（新）。
4. 存储：5 张新表 + 读写（P0 可先用 `device_settings` KV 过渡）。
5. 钩子：`SetOperatorMembership` → 入队收敛；`device.heartbeat` → 自愈下发检查。
6. 控制台：三页（等级策略 / 用户与钥匙 / 目录与价格）+ 收敛进度与失败重试面板。
7. 告警：403 激增、同 key 多设备高频、收敛失败超阈值。

### App

- 模型列表零改动；可选加 `GET /api/membership/usage` 的额度页。

## 十、分期（零人工从 P0 就成立）

| 阶段 | 内容 | 结果 | 预估 |
|---|---|---|---|
| **P0** | 网关按 key 过滤 `/v1/models` + 平台 `GatewayClient/Provisioner/Deliverer` + 管理接口触发收敛 + 控制台最小页（策略 + 用户状态） | 从"管理接口改等级"开始，后面**全自动**：钥匙自动建、设备自动下发、模型列表自动出现（先把链路跑通，兑换放 P1） | 2～3 天 |

## 十一、验收清单（全部零人工路径）

1. **兑换即可见**：用户在 App 核销一张 plus 卡 → 不碰控制台 → 该用户设备 AI 配置出现 `cc-plus` → App 模型列表出现专属模型。
2. **新设备自愈**：用户换新设备登录 → 心跳后自动补推 provider → 模型列表同上（无需人工）。
3. **模型包强校验**：用 plus 钥匙请求 pro 专属模型 → 403 `not allowed for this key`。
4. **列表按钥匙裁剪**：plus 钥匙 `/v1/models` 只返回 plus 模型包（改造后）。
5. **额度自动拦**：额度调到极小 → 下一次请求被拒（`daily cost limit reached`）；续费后自动恢复。
6. **到期自动收回**：把 `expires_at` 设为过去 → 自动降级、钥匙收紧/禁用、设备 provider 撤除。
7. **策略变更广播**：控制台把某模型从 plus 移到 pro → 所有 plus 用户自动失去它（钥匙与设备配置同步收敛）。
8. **网关抖动不丢状态**：停网关 → 收敛任务进入重试队列（设备仍可用旧配置）→ 网关恢复后自动补齐。
9. **审计可查**：控制台能看到每次自动动作（谁触发、何时、结果、失败重试次数）。
10. **对账**：平台日用量 == 网关 `/admin/keys` 的 `usage.cost_micro`。

## 十二、风险与风控

1. 钥匙落在设备上（与现状同级）：只在会员设备下发、支持一键轮换、同 key 多设备高频告警。
2. 模型包与上游耦合：专属模型必须在 `settings.AllowedModels` 内且 `ModelRoutes` 指向稳定上游，否则出现"列表有、请求被全局白名单挡"。
3. 改价影响额度语义：额度按微单位存储；改价前结清历史展示，必要时冻结旧额度。
4. 策略变更的原子性：批量广播用 `policy_version` + 分片任务，失败片段可重试，避免半新半旧。
5. 到期与已用超额：直接禁用并明确提示原因（"额度已用尽"/"等级已变更"），避免用户反复试错。
