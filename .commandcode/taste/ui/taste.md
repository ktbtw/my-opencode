# UI Preferences

- Wants UI/design proposals shown as an HTML mockup, served via a local Python server and opened in the browser, BEFORE implementing in Flutter; explicitly rejects screenshots ("先用html给我看看","不要用截图/图片"). Confidence: 0.9
- HTML previews are also the expected way to understand/verify a change that was already made (not just to approve before coding): when given a prose/markdown description of what changed, they push back ("啥意思，你改成啥样子了，用html展示给我看看") and want an opened-in-browser before/after side-by-side rendering of the actual UI — typically ask for it by name as "HTML 对照图" ("合并思考后是什么样子的？HTML对照图给我看看"), even after the agent already explained the change in text. They also request the before/after HTML comparison as part of approving a fix itself ("你修复一下吧，然后用HTML展示一下修复前后会有什么变化"), i.e. treat the before/after rendering as a deliverable accompanying the code change, not just an optional extra. Confidence: 0.85
- For any design/layout change, must present an HTML prototype for approval first (ideally several alternative options side by side for comparison) and get explicit confirmation before touching the code — never edit the code directly ("必须先用 HTML 原型把方案展示给我看…我确认后再改代码，不要直接改代码"). Confidence: 0.9
- Mockups must match the user's existing Flutter design language, not invent new styles ("按照我当前的flutter已有的设计啊，不要写新的"). Confidence: 0.85
- UI copy must be user-facing Chinese, and must NOT leak business/code logic, internal types, task IDs, status enums, or implementation details ("不要把业务逻辑和代码逻辑当文案"). Confidence: 0.9
- Prefers custom-styled dropdowns/components over native widgets for a consistent, good-looking look. Confidence: 0.75
- Prefers light themes (accepts light blue); explicitly dislikes dark themes and blue-purple color schemes. Confidence: 0.6
- Wants responsive layouts (adaptive to mobile and PC/web), and treats mobile as a first-class target that should be optimised in its own right — not the desktop layout simply squeezed into a narrow bubble (pushes back with "移动端没有单独优化吗？" when mobile only shows one squashed preview). Confidence: 0.8
- Dislikes pages assembled from several separate stacked cards; prefers one cohesive surface ("更整体") where sections are grouped by whitespace and heading hierarchy rather than nested borders/cards. Confidence: 0.7
- Dislikes UI overflow/occlusion; wants consistent component heights, alignment, and unified icon styling (icons redrawn in the primary color, same style). Confidence: 0.65
- Does not accept raw English error strings surfacing in the UI — third-party/backend error text plus low-level runtime/parser/OS errors (e.g. "unsupported content type", "invalid ...", "file too large", "JSON Parse error: Unrecognized token '<'", `Executable not found in $PATH: "ffmpeg"`) must not be passed through untranslated; they report such leaks as bugs to fix. User-visible error/diagnostic text should be Chinese, friendly, and state the actual cause (e.g. "上游返回了错误页面（HTTP 502）" instead of a parser exception), plus a retry hint. Confidence: 0.7
- Dislikes redundant UI: when a status/flow already has an inline hint, wants the state folded into that hint's existing copy (e.g. one line "流程标题 · 当前阶段") instead of adding a separate block/panel or step-by-step chips next to it — explicitly calls layered status displays "太冗余". Confidence: 0.75
- Treats the loss of already-produced reply content as a defect in itself: when a task reaches a terminal state (user stops it, or it fails), the body/thinking/tool-call history the user has already seen must stay rendered and the terminal state must appear only as an additive hint (e.g. a light "任务已停止" note) — the bubble must never be collapsed into just a status/error string ("气泡直接全部变成了'停止任务'。之前的正文输出、思考输出还有工具调用全都不显示了。其实这也是一个问题，需要修复一下"). Confidence: 0.7
- Wants one task in the chat transcript to read as a single continuous flow — consecutive rounds' thinking merged into one growing block and adjacent replies merged into one continuous body, with background-task completions shown as inline lines inside it; repeated per-round thinking blocks that make it look like the task was restarted are a defect ("每一次后台任务完成，我看那个AI的思考链好像重新发起了一次任务一样"). Confidence: 0.6
- Wants chat attachments to be interactive rather than inert preview chips: images should open into a viewer they can pinch-zoom (plus rotate/save), and text/JSON/code files should open in a separate page where they can be edited and shown with syntax highlighting. Confidence: 0.65

- When reviewing an HTML mockup, verifies it was derived from the app's actual current rendering and rejects impressionistic redraws ("你有根据当前真实的显示给我做HTML吗？"); expects the real styles/values/dimensions to be read out of the code before the mockup is drawn. Confidence: 0.75
- Judges the agent's decorative/flashy design proposals as ugly ("这个嵌在内部的UI有点丑啊，你怎么设计成这样了？", "太丑了，还是现在这样吧") — even after asking for something "更炫酷", they end up preferring the existing restrained look, so default to the app's current visual language and keep decoration minimal. Confidence: 0.65
- For pickers with fixed presets (e.g. video duration choices), wants a custom-value input added inside the same bottom sheet rather than being limited to the presets. Confidence: 0.6
- Wants the chat input toolbar to remain a single, horizontally-scrollable row: new/changed controls (e.g. image-generation option chips) should be merged into that same row and reached by swiping right, and adding a separate extra row above/below the toolbar is unwanted ("为什么要上面多加一行？…都同一行，马上开始吧"). Confidence: 0.7
- Dislikes redundant action chrome overlaid on media thumbnails — no "查看"/"放大"/"保存" bar on top of an image when the whole item is already tappable; a direct tap should open/view it ("不需要加一个查看的显示，直接默认点击就是查看"). Confidence: 0.65
- Expects loading/progress UI to surface whatever is already known about the request rather than one generic spinner card — e.g. if N images were requested, show N placeholder cells/占位网格 reflecting the requested count ("为什么正在生成的时候只是一张进度卡呢？不是可以看到用户请求生图的数量吗？"). Confidence: 0.6
- Expects multi-image results to be laid out so all are visible together (adaptive grid: 1 large, 2–4 two columns, 5+ three columns, caption showing "· N 张") rather than stacked full-width cards that read as a single item ("我在移动端只能看到一个预览啊，根本看不出网格来"). Confidence: 0.6
- Labels/captions on generated results must be derived from the actual content type instead of a hardcoded string reused across types: a video result rendering under a "生成图片" caption is reported as a defect ("明明是生成视频的，它渲染出来的气泡框居然是生成图片"). Confidence: 0.6
