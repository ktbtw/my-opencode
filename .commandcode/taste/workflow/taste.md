# Workflow Preferences

- Wants every code change to end with a version number bump plus version notes (更新版本号/版本说明) before building/deploying. Confidence: 0.9
- Prefers deploying/building only the components that actually changed, and objects to blanket "deploy all" (e.g. running `deploy.sh all` for a Flutter-only change). Confidence: 0.85
- Prefers full git commits as backups (全量提交), and explicitly wants the working tree committed as a rollback point BEFORE starting a change ("开始改吧，记得先git提交备份一下"); still prefers scoped deployment of just the changed parts. Confidence: 0.85
- Before a full release (or to validate a change), wants a client build (e.g. Flutter APK) compiled and installed on their own physical device so they can test it personally — expects the agent to do the whole thing (build release APK, `adb install -r` overwrite-install onto the USB-connected device, verify the installed version) rather than just producing the artifact. Confidence: 0.9
- Expects real, production-like end-to-end testing (including edge cases) before shipping; repeatedly asks "都测试完成了吗". Confidence: 0.85
- Typecheck/type analysis alone does not count as testing: after a fix they ask "你改完没有做模拟测试吗" and require a complete run of the actual flow afterwards ("修复完之后做一次完整的测试"), explicitly authorising use of the real upstream model/service to do it ("你可以使用对用的视频模型进行测试") — i.e. exercise the feature end to end against the live service with the real model, not just local static checks. Confidence: 0.8
- Prefers parallel/async execution for installs, downloads, uploads, and reporting; also wants chunked parallel transfer for large files. Confidence: 0.8
- Strongly prefers domestic (China) mirrors over GitHub/official sources when downloading runtimes, packages, and dependencies ("镜像下载优先","不要走 github"). Confidence: 0.9
- Diagnoses problems via server/cloud logs and expects detailed, per-module timing and step logs to be added to help future comparison. Confidence: 0.8
- Wants plans, checklists, unfinished-item lists, and design docs recorded into local files (markdown) rather than only kept in chat. Confidence: 0.8
- Does not want unnecessary rebuilds/redeploys of artifacts (e.g. re-uploading the runtime env or rebuilding when nothing changed). Confidence: 0.75
- Runs multiple agents concurrently on the same repository/branch, so edits should be scoped to the files the agent itself changed (avoid `git add -A` / blanket checkouts) and the other agent's in-progress work must be left untouched. Confidence: 0.7
- Grants the agent direct access to live infrastructure for diagnosis — expects it to connect to the production database (and server) and query real data/logs to find the cause rather than reasoning only from code ("你可以连接线上数据库，看看是啥原因"). Confidence: 0.7
- Once issues are identified, wants the agent to go ahead and fix them all immediately rather than only the top-priority subset it recommended ("你都修复一下吧", "马上修复一下吧"), including secondary bugs the agent discovers along the way. Confidence: 0.7
- Comfortable authorising the agent to make direct writes/changes to production data and services (e.g. promoting a user's membership tier in the live database), not just read-only diagnosis. Confidence: 0.65
- Expects the agent to follow the repository's existing documented process/guide (e.g. 更新发布指南.md) rather than inventing a new approach or stopping to ask for extra confirmation when the guide/scripts already exist. Confidence: 0.7
- Treats a release as a single flow — bump version → commit release notes → build → deploy → push to the remote (setting upstream when unset) — and wants it carried through end to end; delegates it with a single terse instruction ("更新版本号编译发布吧") expecting the agent to determine the new version number and notes itself. Confidence: 0.7
- Treats the backend service as part of a release, not only the client/CLI artifacts: asks for it to be recompiled, updated and restarted in the same breath as the other components ("后端也编译更新重启一下"). Confidence: 0.65
- Expects temporary build/work directories on build machines not to be left accumulating indefinitely — wants throwaway artifacts cleaned up after use (and the documented process changed so they don't pile up) rather than a new per-version directory kept forever. Confidence: 0.6
- Wants UI/layout changes deployed to the web version first so they can personally test in the browser before anything is finalized ("你先推到web，我测试一下看看"), rather than relying only on the agent's own screenshots/golden tests; repeats this request until it's done, so treat pushing the frontend to web as part of finishing the task. Confidence: 0.75
- Web/deployed builds must not hard-depend on foreign CDNs at runtime (e.g. Flutter Web pulling CanvasKit from www.gstatic.com) — engine/asset files should be self-hosted and served same-origin, since foreign domains are blocked or slow through their China proxy setup. Confidence: 0.55
- Keeps browser automation installed on their Mac (`agent-browser`) and expects Web/front-end problems to be reproduced and re-verified in a real browser — ideally the browser they actually use (Edge) — rather than inferred from `curl`/HTTP status codes or left as "couldn't reproduce"; when one browser passes a test they will still direct the agent to validate against the other ("chrome 可以，你试试 edge"). Confidence: 0.7
- Runs Clash (system-proxy mode, TUN off) on their Mac, so network diagnosis must account for proxy routing: their browser traffic goes through the proxy while the agent's shell `curl` may be direct, so "it works from here" is not proof it works for them. Confidence: 0.55
- Expects a root-cause/bug conclusion to be backed by an actual reproduction (a written test/simulation, and multi-device/concurrent scenarios where relevant), not just static code reading — challenges over-confident diagnoses ("你确定是对的吗？你有做过模拟测试吗？…这种复现你有做过吗？") and wants the agent to clearly separate what is verified by a repro from what is still a code-reading hypothesis, plus a concrete plan to reproduce the rest. Confidence: 0.75
- When offered a menu of verification/repro options to choose between, wants the agent to just go and run them all ("那你应该都验证一下试试") instead of stopping to ask which subset or order to do first. Confidence: 0.65
- For reproducing/diagnosing bugs, prefers simulation over touching real hardware: explicitly tells the agent NOT to drive the physical phone ("你不要按真机啊") and instead to call the corresponding API to simulate the test, reusing the project's existing integration/API test scaffolding (fake device + WS) rather than poking the UI. Confidence: 0.85
- Suspects concurrency/race conditions in the system and wants the agent to actively hunt for them with concurrent stress tests ("可能是会有并发或者是竞态的问题吧，你找一下看看") when investigating intermittent or hard-to-reproduce bugs. Confidence: 0.6
- Expects a bug fix to be delivered together with a formal regression test that reproduces the original defect (converted from the throwaway repro), and for that test to be proven to actually catch the bug — the agent temporarily reverts the fix to confirm the test fails without it — before declaring the fix done. Confidence: 0.6
- Wants the definition of "done" for a fix to include running the full test suite of every touched component (e.g. `go test ./internal/...` for the backend, `flutter test` for the app) plus the component's static analysis (`flutter analyze`), and to call out pre-existing lint/info items as not introduced by the change. Confidence: 0.6
- Treats the git commit as a mandatory step of any deploy/release (not an optional follow-up to propose) — after the agent shipped a release but reported "我没有做 git commit（你没要求）", the user pushed back with "那你当然要做一下提交呀", so leaving the working tree uncommitted and offering to commit later reads as an unfinished task. Confidence: 0.75
- When releasing client builds, expects every platform target covered — Windows EXE and macOS DMG as well as the Android APK (plus Web) — not just the one platform implied by the change; will explicitly ask for whatever is missing ("Windows和Mac的也需要"). Confidence: 0.6
- For bugs on a specific platform/environment they own, expects the fix to be actually executed and verified on that real target machine (e.g. "你在windows跑一下"), not just on the dev Mac or by code reading — including an old-vs-new A/B run on that machine. Confidence: 0.6
- When reporting a bug/symptom, expects the agent to also proactively audit for OTHER instances of the same class of problem the user may not have noticed ("除了这个问题，你看看有没有其他我没有发现的…遗漏的问题"), reporting them ranked by severity, rather than fixing only the single reported case. Confidence: 0.7
- Keeps track of which build is actually live on their own machine and asks to confirm it ("当前我的Windows里面运行的是新版的吗？"); expects the agent to clearly separate throwaway/isolated verification instances (temp port, in-memory DB) from the real installed deployment and state plainly whether the fix is running yet or still only in the working tree. Confidence: 0.65
- Expects usage/diagnostic statistics to describe their setup as it is now, not a stale sample from a partial API window: when a report quotes old providers/models they push back ("你这些统计好像有点过时了呀，我现在用的都不是这些，我用的是订阅DS") and want the analysis re-run against the authoritative full source (e.g. the local session DB) filtered by the provider/model they are actually using. Confidence: 0.6
- Wants the whole remaining backlog finished in one go, not a chosen subset: when the agent ends a turn by offering a pick between outstanding tasks (even a simple "先做 A 还是先做 B？"), the user answers "剩下的都完成一下" and expects every pending item done — this applies to feature/implementation work, not just the bug-fix and verification cases already noted. Confidence: 0.6
- When offered optional improvements/optimizations on top of already-finished work, prefers to defer them ("暂且先不优化吧") and get the pending changes shipped first — shipping existing work takes priority over starting new scope. Confidence: 0.55
- For "content is missing" symptoms, expects the agent to establish ground truth from the authoritative upstream record (e.g. the agent-side session data served by the opencode instance actually running on their device) and diff it against the client's local store — to distinguish "never produced" from "produced but dropped" — instead of reasoning from client state alone ("你对比一下设备里面运行的 opencode 的对话记录，这个是怎么缺失的呢"). Confidence: 0.6
- Insists each version's release notes contain only what is genuinely new in that release and be checked against every earlier version's notes for duplication ("这个更新说明跟之前其他版本的更新说明没有重复吗？你都看一下。") — a changelog that re-lists previously released items is a defect to fix and redeploy, even after the release already shipped. Confidence: 0.8
- Expects the agent to drive their Windows test machine directly over SSH for diagnosis (log reading, version checks) as readily as the Mac; nested-quote PowerShell one-liners get mangled through the ssh/cmd layers, so scripts should be sent base64-encoded (UTF-16LE via `powershell -EncodedCommand`) rather than fighting shell escaping. Confidence: 0.6
- Wants device-side tool/dependency provisioning to be on-demand and self-service: when a feature needs a binary on the device (e.g. FFmpeg for video first-frame extraction), the app should check the device at the point of use (on switching to that model) and, if missing, show a confirmation dialog that transitions in place into a live download/install progress dialog with real-time progress — not fail later with an error or require manual installation ("用户切换到视频模型的时候，就检查一下…弹出下载框，用户确认下载之后，就把下载框自动变成下载进度框，实时显示下载进度"). Confidence: 0.7
- Treats the upstream/vendor-side request record as the authoritative anchor for "did this request even happen": they volunteer the provider's request timestamp ("2026/09/30 15:44:49"…"这是我对应的供应商的请求时间") and expect the agent to locate the matching device/agent log record and trace that request end to end — not conclude from an empty/absent log that nothing was sent, but keep looking (other log directories, matching by file mtime rather than filename) until the exact record is found. Confidence: 0.6
- Treats a fix as unsafe-to-ship until the user's normal (unaffected) usage path is shown to still work — asks "会不会影响到用户正常的发消息啊？" and expects a concrete answer/verification that only the intended path changed. Confidence: 0.6
- After a fix that shipped having missed a layer of a multi-stage feature, expects the agent to re-walk the ENTIRE end-to-end flow/pipeline stage by stage (device check → download/install → task submit → poll → retrieve → post-process → deliver → client display), find any remaining breakages anywhere in that chain, and only then bump the version and build/deploy ("顺着这个流程模拟一遍，不要再出错了") — and to report the result as a per-stage status accounting, not just "fixed". Confidence: 0.6
- Expects generated media/results to be served through their own infrastructure, not by handing the client the upstream/vendor URL: they object when tapping play jumps out to the upstream relay ("为什么我点击播放视频就跳转到中转站去了？我们没有自己下载吗？"). Upstream addresses are temporary and require auth (a plain browser open 404s), so the client must fetch/play media via their own download channel served by their backend rather than linking the raw upstream address. Confidence: 0.7
- When the user-visible symptom lives in the client, expects the client app itself to get its own version bump and release as part of the fix — after a backend/CLI-only release they came back with "你更新好了吗？Flutter有更新吗？为什么我点进去还是跳转网页". Shipping only the server/agent side therefore does not count as done; it should be stated per component which layers got a new version and which are still running the old build. Confidence: 0.6
- Holds the agent accountable for earlier "fixed" claims across versions: when the same user-visible symptom recurs after a release that claimed to fix it, they treat it as a defect and push back sharply ("你上个版本不是修复了吗？…那你修了啥？修了个寂寞吗？"). A single user-visible symptom often spans independent layers (server/CLI and client), so a fix announcement must be backed by verifying the exact reported symptom end-to-end on every layer, and clearly stating which layer was and was not covered — not just fixing the one code path that was found first. They keep re-testing each build and will report the symptom back with "又…了" ("视频预览又变成了对话的渲染效果") when a claimed fix did not actually hold, so a "fixed" claim should be treated as unproven until the original symptom is re-verified on the shipped build. Confidence: 0.65
- Prefers fixing the root cause in the code/product so future releases and fresh environments come out correct, over a one-off manual data patch: when offered "只改数据止血（控制台改 + 手动重新下发）" vs a code change that lets the built-in defaults update already-initialized environments, they chose the code path (内置更新机制 + 设备端刷新) and explicitly declined the data-only workaround. Confidence: 0.6
- Treats a configured setting/preset as broken until its effect is observable at the end (model/UI) level: when a saved model prompt preset seems to have no effect ("我明明已经设置好了模型提示词，但是为什么我感觉没有效果呢？"), they judge it by the live behaviour (e.g. asking the model who it is) and expect the agent to trace the whole delivery chain — config storage → per-model matching → injection at task creation → which device/runtime version is actually running — rather than concluding from server logs that "it is technically injected". Confidence: 0.6
